# Upstream Readrops since the fork point

Ticket: `.scratch/appropriate-and-fix/issues/10-research-upstream-since-fork.md`
Surveyed: 2026-09-05, against `readrops/Readrops` on GitHub via the REST API (`gh api`).
Fork point: [`9ebbe038`](https://github.com/readrops/Readrops/commit/9ebbe038d0b1357be1a3713dd3222f51820c7f45) on `develop`, 2025-07-20, "Display tags in TimelineTab and ItemScreen".

## Summary

Upstream has been dormant since the fork. The repository's `pushed_at` is `2025-07-20T16:49:42Z`, the timestamp of the fork commit itself; `develop` still points at `9ebbe038`, `master` still points at [`dcd7a9f3` (v2.1.1, 2025-07-07)](https://github.com/readrops/Readrops/commit/dcd7a9f3), no release has been cut after [v2.1.1](https://github.com/readrops/Readrops/releases/tag/v2.1.1), and the eight other branches all predate 2024. There is therefore nothing to cherry-pick: no commit, no merged PR, no schema change, no dependency bump, no security fix. The Room schema is still version 6, and upstream `develop` was left mid-feature: the tag commits bumped `version` from 5 to 6 and added `Tag`/`TagJoin` to the exported `6.json`, but no 5→6 migration (manual or auto) was ever registered in `DbModule`, so a v2.1.1 install upgraded to this code would refuse to open its database. What did accumulate is on the tracker side: two unmerged PRs (one of them, [#306](https://github.com/readrops/Readrops/pull/306), is a one-file change to the FreshRSS initial-sync item limits that the maintainer pushed back on), and about thirty new issues, of which a handful are directly relevant to a FreshRSS-only client — a still-open "mark all read does not work with FreshRSS" report ([#341](https://github.com/readrops/Readrops/issues/341)), a "sync slows down because old items are never deleted" report ([#359](https://github.com/readrops/Readrops/issues/359)) that is the third pain point stated by another user, a cluster of `FileUriExposedException` crashes when tapping links inside the article WebView ([#354](https://github.com/readrops/Readrops/issues/354), [#357](https://github.com/readrops/Readrops/issues/357), [#358](https://github.com/readrops/Readrops/issues/358), [#355](https://github.com/readrops/Readrops/issues/355), [#353](https://github.com/readrops/Readrops/issues/353)), a default `okhttp/4.12.0` User-Agent that gets 403'd by common blocklists ([#360](https://github.com/readrops/Readrops/issues/360)), a Google Reader login using `multipart/form-data` that Miniflux rejects ([#334](https://github.com/readrops/Readrops/issues/334)), and an unanswered "[Security] Important data breach" ticket ([#347](https://github.com/readrops/Readrops/issues/347)) whose content was never disclosed. Nobody upstream reported duplicated articles for FreshRSS; the duplicate and slowness diagnoses in the map remain LeNews's own to make. The practical consequence for ticket 12 is that every fix is a re-implementation in LeNews's model, and the upstream tracker is useful mainly as a list of bugs to check LeNews against, not as a source of patches.

## 1. Duplicates

Nothing upstream. No issue, commit, PR or release note mentions duplicated articles for FreshRSS or Google Reader accounts after the fork. The only duplicate-related traffic is older and about other services:

- [v2.0.3 release note](https://github.com/readrops/Readrops/releases/tag/v2.0.3), 2024-12-02: "Fix Nextcloud News item duplicates when syncing which would made the app unusable". Nextcloud only, already in the fork. **Irrelevant** after Nextcloud News is deleted.
- [#285 "Remove duplicates links from different feeds"](https://github.com/readrops/Readrops/issues/285), closed 2025-04-13 as a discussion. The maintainer's position: duplicates "should be handled at insertion", which Readrops does for local accounts by guid/link, and for remote providers the provider is responsible. No code change. **Irrelevant** as a fix, but it confirms the fork's design: `GReaderRepository.insertItems` inserts every returned item with plain `@Insert` (`BaseDao.insert`, no conflict strategy) and `Item` has no unique index on `remote_id` — see `db/src/main/java/com/readrops/db/entities/Item.kt` (only `feed_id` is indexed) and `app/src/main/java/com/readrops/app/repositories/GReaderRepository.kt` lines 160-199.
- The `ItemState` table does have a unique index on `(remote_id, account_id)` (`db/src/main/java/com/readrops/db/entities/ItemState.kt`, with a `TODO check potential performance regression at insertion` comment), so read state cannot duplicate; only `Item` rows can.

Verdict: **re-implement in LeNews**. Upstream never added a uniqueness constraint, an existence check or a cursor change, so the map's diagnosis (no constraint, no existence check, `account.lastModified` advanced only after all inserts, so a failed sync replays the same window) stands and has to be fixed locally. Worth noting for ticket 12: FreshRSS's `greader.php` supports a `c` continuation token on `stream/contents` and `stream/items/ids` ([source](https://github.com/FreshRSS/FreshRSS/blob/edge/p/api/greader.php), search `continuation`), which the fork never uses; it fetches one page of `n=2500` with `ot=lastModified`.

## 2. Performance

- [#359 "Readrops sync with nextcloud slows down"](https://github.com/readrops/Readrops/issues/359), open, 2026-06-07, no reply. "Readrops keeps old news entries (one feed now has 2783) and every day the sync gets slower and slower. Did I miss some configuration so old entries are removed?" Nextcloud account, but the mechanism is service-independent: items are never deleted, and the cost grows with table size. **Re-implement**: this is the map's retention decision (mirror FreshRSS, 30-day horizon). No upstream fix exists.
- [#262 "`FolderDao.selectFoldersAndFeeds`: why is SQL query so complex?"](https://github.com/readrops/Readrops/issues/262), open discussion from 2025-02 by christophehenry (the most active outside contributor). Second comment: the timeline reads through `Item` joined to `ItemState` while the drawer reads `Item` only, and "I don't really understand the purpose of `ItemState` here. It's confusing and prone to errors." Related merged PRs [#263](https://github.com/readrops/Readrops/pull/263) (closed unmerged) and [#276](https://github.com/readrops/Readrops/pull/276) (merged 2025-03-16, already in the fork) only touched the drawer query. **Irrelevant as code**, but it is independent confirmation that the `ItemState` split is a liability; LeNews's ticket 13 collapse (single account, read state back on `Item`) removes it.
- No upstream issue, commit or PR mentions indexes on `Item`, `ItemState` join cost, paging changes or item deletion. The timeline query in the fork still does `LEFT JOIN ItemState On Item.remote_id = ItemState.remote_id` with no index on `Item.remote_id` (`db/src/main/java/com/readrops/db/queries/ItemsQueryBuilder.kt` line 49).
- Two crash reports show `androidx.paging` frames in the stack ([#365](https://github.com/readrops/Readrops/issues/365) `Key "109" was already used` in a LazyColumn, [#356](https://github.com/readrops/Readrops/issues/356) `OutOfMemoryError` on return from recents). #365 is exactly the symptom a duplicate `Item.id` key in the paged list would produce, though with autogenerated ids the more likely cause is a Compose key collision in the bottom sheet, and upstream has not analysed it. **Worth checking LeNews against**, not cherry-pickable.

Verdict: nothing to take; upstream never touched the suspects the map names (single `feed_id` index, unindexed `remote_id` join, no deletion, full `ItemState` delete-and-reinsert every sync).

## 3. Sync

No change to `GReaderRepository`, `GReaderDataSource`, `ItemState`, `insertItemsIds` or the sync cursor upstream since the fork. The fork's `insertItemsIds` (`GReaderRepository.kt` lines 208-258) still does `deleteItemStates(account.id)` followed by three bulk inserts every sync. Relevant tracker items:

- [PR #306 "Fetch as many items as possible during the initial sync"](https://github.com/readrops/Readrops/pull/306), open since 2025-05-07, one file (`GReaderDataSource.kt`, 4 lines): replaces `MAX_ITEMS` (2500) and `MAX_STARRED_ITEMS` (1000) with `Int.MAX_VALUE` in the initial-sync calls, to fix [#282 "Some items for some feeds are not fetched"](https://github.com/readrops/Readrops/issues/282) (feeds that have not published recently appear empty after initial sync because the newest 2500 items across all feeds crowd them out). The maintainer refused on 2025-06-02: `Int.MAX_VALUE` "could create a ton of PHP OOM for medium-end instances" (he had reports that 5000 was already too much, see [#116](https://github.com/readrops/Readrops/issues/116), which is why the limit went 5000→2500 in v2.1.0), pagination would be the right tool, and "design wise, I am against fetching the entire database". The PR's head is 27 commits behind `develop` and would need a trivial rebase. **Do not cherry-pick as is**; **re-implement the idea** in LeNews as continuation-based paging (`c` parameter, see section 1) with a per-page `n` in the low thousands, which serves both the "empty feed after first sync" bug and the map's "mirror FreshRSS" retention rule. Also note christophehenry's second point in the PR body: a regular sync that has been away long enough to have more than 2500 new items silently drops the excess, because `ot` is not paginated either.
- [#341 "Mark all read does not work with FreshRSS"](https://github.com/readrops/Readrops/issues/341), open since 2025-09-26, v2.1.1, Pixel 9 Pro / Android 16: mark-all-read from the Timeline "Articles" view, then pull to refresh, and "all articles appear again"; marking read from inside a category works. A second user (2026-04-03, CommaFeed via Fever) says "marking as read or starring items is not triggering any endpoint call". Nobody upstream diagnosed it. In the fork, `Repository.setAllItemsRead` (`app/src/main/java/com/readrops/app/repositories/Repository.kt` lines 172-190) does, for a separate-state account, `upsertAllItemsReadStateChanges` then `ItemStateDao.setAllItemsRead` inside one transaction, so the change rows are produced and the next sync should push them via `setItemsReadState`. The cause is therefore not the obvious one and needs a reproduction: candidates are the filtered "Articles" view calling the id-list path rather than the account-wide one, the push happening before `lastModified` is advanced so the `readIds` list from `stream/items/ids` (fetched in the same `awaitAll` as the push, `GReaderDataSource.kt` lines 59-80) comes back stale, or the 2500-id cap on `getItemsIds` silently truncating the read list. **Worth reproducing in LeNews before ticket 13**, since the history feature makes mark-all-read a first-class action. Re-implement, nothing to take.
- [#337 "Sync read state with FreshRSS server"](https://github.com/readrops/Readrops/issues/337), closed 2025-08-31 by the reporter as a transient DNS problem. **Irrelevant.**
- [#334 "Can't add Google Reader API account (Miniflux)"](https://github.com/readrops/Readrops/issues/334), open, 2025-08-11: `accounts/ClientLogin` is sent as `multipart/form-data` (`GReaderDataSource.login` builds a `MultipartBody`, `api/src/main/java/com/readrops/api/services/greader/GReaderDataSource.kt` lines 17-31); Miniflux logs "Empty username or password". FreshRSS accepts it, so LeNews is not affected, but switching to `application/x-www-form-urlencoded` (which is what the original Google Reader protocol used and what every other client sends) is a two-line change that removes a FreshRSS-specific assumption. **Low-priority re-implement**; cannot be cherry-picked, no upstream patch exists.
- [#60 "Sync already read articles"](https://github.com/readrops/Readrops/issues/60) was closed 2025-07-27 (one week after the fork) with no code, and [#143](https://github.com/readrops/Readrops/issues/143) was closed 2025-03-02 with the maintainer's explanation of the two sync modes (initial: 2500 unread items; classic: items since `lastModified` plus the full unread/read/starred id lists). **Irrelevant**, documented here because ticket 12 will re-decide what the initial sync fetches.

## 4. Tags

Upstream did nothing after the fork. The five tag commits that end at `9ebbe038` (`cb1526ad` fetch tags from FreshRSS, `527c3901` insert FreshRSS item tags, `a649527c` tag upsert, `455194ec` parse RSS1/RSS2/Atom/JSON Feed categories, `9ebbe038` display tags) are the entire feature, and the per-item query the code review flagged (`TagDao.selectItemTags`: `Select Tag.* From Tag Inner Join TagJoin on Tag.id = TagJoin.tag_id Where item_id = :itemId`, `db/src/main/java/com/readrops/db/dao/TagDao.kt` line 20) was never revisited. The feature never shipped in a release; v2.1.1 predates it (`master`'s `db/schemas` directory stops at `5.json`, `develop`'s has `6.json`).

- [#54 "Support for tags"](https://github.com/readrops/Readrops/issues/54), open since 2020, still open. Alkarex (FreshRSS maintainer) added a single comment on 2025-07-27 linking [FreshRSS discussion #7759](https://github.com/FreshRSS/FreshRSS/discussions/7759) (not fetched, see Method). The 2020 exchange records the design intent that matters for LeNews: a FreshRSS label is many-to-many (one article under several labels, and the labels are streams you can list with `stream/contents/user/-/label/<name>`), and the maintainer's counter-proposal was to treat labels like folders. The fork implements the display half only (chips on the item), not label-as-stream filtering.

Verdict: **LeNews's own call**, nothing to take. If tags stay, the per-item query has to be replaced locally (a join in `ItemsQueryBuilder` or a `group_concat`); if they go, `Tag`, `TagJoin`, `TagDao`, `TagJoinDao`, `GReaderFoldersTags` and the two tag tables come out together, which the schema reset (section 5) makes free.

## 5. Schema

- Upstream Room version at `develop` HEAD: **6** (`db/src/main/java/com/readrops/db/Database.kt` line 37, identical in fork and upstream). Exported schemas: `1.json` to `6.json`.
- Migrations present: `MigrationFrom1To2`, `MigrationFrom2To3`, `MigrationFrom3To4`, `MigrationFrom4To5` (manual, `Database.kt` lines 59-117, registered in `db/src/main/java/com/readrops/db/DbModule.kt`). **There is no 5→6 migration.** The tag commits ([`527c3901`](https://github.com/readrops/Readrops/commit/527c3901), [`a649527c`](https://github.com/readrops/Readrops/commit/a649527c)) raised `version` to 6 and added the `Tag` and `TagJoin` tables to the exported `6.json`, but `Database.kt` declares no `autoMigrations` and `DbModule` registers nothing past `MigrationFrom4To5`; there is no `fallbackToDestructiveMigration()` either. Upgrading a v2.1.1 install (schema 5) to this code would throw Room's "A migration from 5 to 6 was required but not found". Upstream never got to fix that; it is the clearest sign `develop` was abandoned mid-feature.
- **Migrations added after version 6: none.** No `Item` or `ItemState` column changed after the fork. `Item` columns at HEAD: `id, title, description, clean_description, link, image_link, author, pub_date, content, feed_id (indexed), read_time, read, starred, remote_id`. `ItemState` columns: `id, read, starred, remote_id, account_id` with a unique index on `(remote_id, account_id)`.

Verdict: **irrelevant**. The map has already decided that the `applicationId` change resets the schema, so no upstream migration would ever have to be honoured; and there is none anyway.

## 6. Security

No change upstream to `AuthInterceptor`, `ItemWebView`, or `network_security_config.xml` since the fork (all three files at `develop` are the fork's files). Tracker items:

- [#347 "[Security] Important data breach"](https://github.com/readrops/Readrops/issues/347), open, 2025-10-18, no labels, no reply, zero comments. The reporter emailed the project's published contact address on 2025-09-24, got no answer, and opened the issue without details "to avoid more compromission", advising users to "avoid using a central authentication method for your RSS feed (Nextcloud, ...) until the issue is fixed". The maintainer never responded. **Cannot be assessed**; the only hint is "Nextcloud", which LeNews deletes. Worth keeping in mind when ticket 13 reviews how credentials are stored and sent: the fork keeps `login`/`password`/`token`/`writeToken` in the `Account` row and `AuthInterceptor` (`api/src/main/java/com/readrops/api/utils/AuthInterceptor.kt`) adds the `Authorization` header to every request of the shared `OkHttpClient`, whatever the host.
- [#354](https://github.com/readrops/Readrops/issues/354), [#357](https://github.com/readrops/Readrops/issues/357), [#358](https://github.com/readrops/Readrops/issues/358), [#355](https://github.com/readrops/Readrops/issues/355) (all `FileUriExposedException`) and [#353](https://github.com/readrops/Readrops/issues/353) (`ActivityNotFoundException` for `dat=denied:`), five reports between 2026-01 and 2026-05, four of them explicitly FreshRSS, two on GrapheneOS/Android 16. Common stack: `ItemWebView$1.shouldOverrideUrlLoading` → `ItemScreen` `openUrl`/`openInCustomTab` → `startActivity` with a `file://` URI. Cause: `ItemWebView.loadText` loads the article with `loadDataWithBaseURL("file:///android_asset/", ...)` (`app/src/main/java/com/readrops/app/item/view/ItemWebView.kt` line 73), so relative or scheme-less links in article HTML (`//www.youtube.com/embed/...`, `../memory/dreams.md`) resolve to `file://...` and are handed straight to an `Intent.ACTION_VIEW`. `shouldOverrideUrlLoading` returns `true` for every URL without checking the scheme. **Re-implement**: whitelist `http`/`https` (and maybe `mailto`) before firing the intent and drop the rest; also consider a non-`file` base URL (`https://localhost/` or the feed's site URL) so relative links resolve to something meaningful. This is the most frequently reported crash of the year and the app's `javaScriptEnabled = true` WebView with a `file:///android_asset/` base is the same surface the code review flagged.
- [#360 "App uses User-Agent containing 'okhttp' that is common in blocklists"](https://github.com/readrops/Readrops/issues/360), open, 2026-07-08, FreshRSS behind nginx returns 403. The fork sets no User-Agent (`api/src/main/java/com/readrops/api/ApiModule.kt` only adds `AuthInterceptor` and `ErrorInterceptor`), so requests go out as `okhttp/4.12.0` (visible in the Miniflux log quoted in #334). **Re-implement**: a one-line interceptor setting `User-Agent: LeNews/<version>` — trivially in scope for the rename ticket, and it stops leaking the library version.
- [#348 `ApiUtils.md5hash` drops leading zeros](https://github.com/readrops/Readrops/issues/348): Fever API key only. **Irrelevant** once Fever is deleted (and `ApiUtils.md5hash` should go with it).
- `network_security_config.xml` still has `cleartextTrafficPermitted="true"` and trusts user CAs; no upstream discussion. LeNews's decision.

## What this means for ticket 12

- There is no upstream patch for any of the three pain points; each is a LeNews design decision and implementation.
- The upstream tracker independently confirms two of the map's diagnoses (never-deleted items slow the sync, #359; the `ItemState` split is confusing and mismatched across queries, #262) and adds one the map did not have (mark-all-read may not be pushed to FreshRSS, #341).
- FreshRSS's Google Reader endpoint supports continuation paging that the fork never used; PR #306 and issue #282 are the case for using it during the initial sync.
- The one small upstream contribution worth taking verbatim is PR #363 (swipe-to-page toggle), and only after ticket 13 settles the item screen.
- Two cheap hardening items surfaced by users, not by the code review: scheme-check links before `startActivity` (five crash reports), and set a real User-Agent (one 403 report).
