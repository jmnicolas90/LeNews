# Appropriate the fork as LeNews and fix what hurts

Label: wayfinder:map
Charted: 2026-09-05

## Destination

A repo that is unmistakably **LeNews** — its own name, package, identity and docs, carrying no trace of upstream ownership beyond the GPL attribution it is legally obliged to keep — that is a **FreshRSS-only, single-account** Android client, builds and passes a **green, executable quality gate** both on this machine and in CI (instrumented database tests included), in which **every finding of the 02-09-2026 code review** has been either fixed or consciously ruled out of scope, and in which the **three pain points are gone**: the app no longer slows down as articles accumulate, an article is never stored twice, and there is a chronological **history** of everything that became read so a dismissed article can be found again.

### Settled while charting

Decided in conversation on 2026-09-05. Not tickets.

- **Scope** — Ding's shape plus the three pain points: repo is ours, gate is green, every review finding fixed or ruled out, slowness, duplicates and history solved. Feature work beyond that is a later map.
- **Name** — **LeNews**. `applicationId` and `namespace` become `app.lenews`, source package `app.lenews.*`, house style of `app.ding` / `app.loquace`. Renaming the applicationId makes the phone treat it as a new app: fresh install, re-login, full re-sync. That is accepted, and it means **no migration from the Readrops schema is ever needed** — the schema can be reset.
- **Hard fork** — upstream is never merged again. Charting assumed upstream was still active with ~14 months of `develop` to survey; ticket 10 found it went dormant at the fork commit, so the hard fork costs nothing and every fix is LeNews's own.
- **FreshRSS only** — local RSS parsing, Nextcloud News and the Fever API are deleted (ticket 04). The Google Reader API code path stays, since that is how FreshRSS is spoken to.
- **Single account** — one FreshRSS account, so the account layer and the per-account separate read-state table can collapse. The account screen becomes a login screen. Exact model is ticket 12's to decide.
- **History** — *every* transition to read enters history: opening an article, swiping it, mark-all-read, and a read observed at sync (read on the FreshRSS web UI) stamped with the sync time. One chronological list, newest first. The timestamp is local only; the Google Reader API cannot store it. The user accepts that mark-all-read at 300 articles a day fills the list — history is simply "everything that became read, in order".
- **Retention** — two rules and one exception that covers both. **Mirror**: the local store holds what FreshRSS holds, so an article FreshRSS no longer returns is dropped locally — **unless it is starred, or still within the horizon**. **Horizon: 30 days**, counted from when the article **became read** and not from when it was published or fetched: past that a read article is no longer kept, whatever the server still has — **unless it is starred**. **Starred articles survive both rules**, whatever the horizon says and whatever FreshRSS returns. The user does not search for something seen months ago. `CONTEXT.md`, `CLAUDE.md` and ticket 15 state the same predicate in the same words; if one of them drifts from the other three, it is the one that is wrong.
- **Slowness diagnosis** — the installed app is a store build and the user's database is off limits regardless, so nothing real is pulled. Diagnosis runs on an emulator against a database seeded with a year of articles (ticket 11). The code already names the suspects: `Item` has a single index (`feed_id`); FreshRSS accounts read state through `LEFT JOIN ItemState ON Item.remote_id = ItemState.remote_id` with no index on `Item.remote_id`; items are never deleted; every sync deletes and reinserts all `ItemState` rows for the account.
- **Duplicates** — the sync inserts every returned item with no existence check and no uniqueness constraint; the sync cursor (`account.lastModified`) is advanced only after all inserts, so any failure in between replays the same items next time. Ticket 09 then showed re-delivery is *normal*: FreshRSS's `ot` filter is inclusive and also matches articles whose content changed since, so the boundary article comes back on every sync and any edited article comes back once more. One account, so the review's multi-account join theory does not apply here.
- **Gate** — Ding's `scripts/check.sh` shape plus a **final instrumented stage** on the existing `bench-pixel6-aosp` emulator (API 36, pure AOSP), mirrored in CI on GitHub's emulator runner. All three pain points are database-level and Room migration/DAO/query tests only run on a device.
- **Distribution** — public GitHub releases, as Ding. Not the Play Store, not F-Droid.
- **Tracker** — local markdown under `.scratch/`, committed.

- [The slowdown measured on a year-sized database](issues/11-measure-timeline-slowness.md) — `TimelineSlownessBenchmarkTest` in `db/src/androidTest`, seeding 110,000 articles / 100 feeds / 10 folders / ~6,000 `ItemState` rows / 44,000 tag joins (219 MB) in 2.3 s on `bench-pixel6-aosp`, against a 10,000-article control, in five index passes. **The timeline is linear in the number of articles stored**: first page 7.2 ms at 10k and 90.2 ms at 110k, Paging's `SELECT COUNT(*) FROM (query)` 7.6 ms and 125.3 ms, and it is paid again on every invalidation — so one article marked read costs about **215 ms of database work** at a year's size. The plan never says `SCAN Item`; it says `SEARCH Item USING index_Item_feed_id` once per feed and then `USE TEMP B-TREE FOR ORDER BY`, which visits all 110,000 rows and sorts them to return fifty. **Adding the indexes changes nothing on its own** — with `Item(pub_date)` created the page stayed at 90 ms and the plan did not move a line; with `ANALYZE` on top it drops to **0.4 ms** (x225), and a forced `INDEXED BY` proves the index could always have served it. `COUNT(*)` is the one thing no index reaches (81 ms after), so only retention bounds it. **And the second headline is not a query at all**: `GReaderRepository.insertItemsIds` matches 5,000 capped ids against a 1,000-element starred list with `any`/`remove`, **1,570 ms of pure CPU per sync** at either size — ten times everything else the sync does to `ItemState` (delete 2.3 ms, Room's `insert(List)` 86 ms against 21 ms for the same rows by compiled statement). Suspects: single index on `Item.feed_id` **confirmed** and primary for the timeline; `Item.remote_id` measured **in isolation** and splitting three ways — **cleared** for the all-items timeline (90.6 ms with and without it), **the whole fix** for the unread timeline (77.7 -> 2.8 ms) and **necessary but not sufficient** for the drawer, where the index alone leaves 73.8 ms at 74.3 ms and it takes `ANALYZE` (1.2 ms) or `ItemState(account_id)` as well (1.3 ms) before the planner drives from `ItemState`; items never deleted **confirmed** as what drives all of it; `ItemState` delete-and-reinsert per sync **confirmed** once the production path is measured, at 1.66 s; the API caps **do not** bound `ItemState` — one mark-all-read takes it from 5,955 to 110,000 rows in 334 ms and makes the next sync's delete cost 143 ms instead of 2.3; per-article tag query **cleared as growth** but 6-11 ms a page through the real suspend DAO, ~90% of it Room, not the 0.9 ms raw SQL showed. x86_64 emulator on a fast host, so the ratios are the finding and not the milliseconds. Default G7 cost: the 10,000-article control, 22 s; the year-sized run is opt-in behind `-Pandroid.testInstrumentationRunnerArguments.lenewsBenchmark=full` and takes 54 s.

- [Define the article store: identity, state, sync, mirror, history](issues/12-define-article-store-model.md) — grilled in two rounds, every recommendation taken, written as `docs/article-store.md` plus `docs/adr/0001-freshrss-id-is-the-article-key.md`; no code. **The FreshRSS 64-bit id is the article's primary key**, decimal, no autoincrement and no `remote_id` string; a re-delivered id updates content and keeps state. **`read`, `starred` and `read_at` are columns on the article**; `ItemState`, `ItemStateChange`, `useSeparateState`, every `account_id` column and **tags** are gone, `Account` stays as one row holding URL, name, tokens and the cursor. **A `PendingChange` table** (one row per article, `read?`/`starred?`) is uploaded first in batches of at most 998, cleared only where the value still matches, and the server's lists never touch a column with a pending value. **Sync**: all network calls first, then one transaction — feeds, article upserts, read state, starred state, the retention delete, the cursor, `PRAGMA optimize` — that rolls back whole; state comes from three paged `stream/items/ids` walks (all, unread, starred), content from `stream/contents`, and starred ids the store lacks have their content fetched. **Retention is one delete**: `starred = 0 AND ((read = 1 AND read_at < now − 30 days) OR (read = 0 AND id absent from the server's full list))`, horizon a named constant, a starred article whose feed is unsubscribed the one case starred does not survive. **History is `read_at`**, stamped on every becoming-read by any route (sync time for a read learned at sync), cleared by unread, no history table. **Initial sync** pulls all unread and all starred, paged, no cap, no read articles. Six indexes and a budget: every first page and the drawer under 10 ms on the 100k seeded store, `COUNT(*)` under 20 ms at the 20k retention leaves.

- [One authenticated client for FreshRSS, one plain client for everything else](issues/18-http-client-credentials.md) — `HttpClients` in the `api` module holds the pair and is the only place either is built.
